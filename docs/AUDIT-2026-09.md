## 1. Méthode

| Étape | Détail |
|---|---|
| Lecture du code | Lecture intégrale des ~18 300 lignes du dépôt (shared, server, client, SQL, CSS, HTML, scripts de déploiement, docs). |
| Build | `npm install`, `npm run build:shared`, typecheck client et serveur, build Vite de production. Tout passe sans erreur. |
| Banc de charge serveur | Room `ArenaRoom` exécutée hors réseau, remplie de bots (15, 25 et 60), temps simulé accéléré (jusqu'à 10 minutes de jeu), mesure du coût de chaque tick, de la taille des patchs Colyseus reçus par un client et des évènements diffusés. Outil versionné : [`tools/bench-server.js`](../tools/bench-server.js). |
| Profilage CPU | `node --cpu-prof` sur 90 s simulées avec 60 bots, agrégation du temps par fonction. |
| Sessions réelles | Serveur de production local + client buildé, pilotés par Chromium headless (Playwright) : 6 sessions desktop (4 thèmes, qualité High et Potato), 1 session mobile 390×844. Mesure du trafic WebSocket reçu via le protocole DevTools. Rendu logiciel (SwiftShader) : les FPS observés (~10-40) ne sont **pas** représentatifs, seules les images et le trafic le sont. |
| Captures | Sélection jointe dans [`docs/audit-2026-09/`](audit-2026-09/) : elles servent d'état de référence pour mesurer les progrès. |
| Audit des dépendances | `npm audit --omit=dev`. |

Limites : aucune partie avec de vrais joueurs humains, pas d'accès aux métriques de production, pas de test sur GPU réel. Les constats de ressenti (game feel) sont déduits du code et des captures ; ceux marqués « à valider en playtest » doivent être confirmés en jeu.

## 2. Synthèse

**Verdict** : blades.io a un socle technique sérieux (serveur autoritatif propre, contrat `shared/` clair, système de thèmes bien conçu, presets de qualité, code commenté avec rigueur) et un concept qui fonctionne (anneaux de lames, lancer, snowball). En l'état, c'est un **prototype avancé** plutôt qu'un jeu prêt à retenir des joueurs : le combat n'est pas fiable visuellement, la première minute est punitive, la progression plafonne vite, il n'y a pas de raison de revenir, et l'économie de trophées est exploitable.

## 3. Chiffres mesurés

### Serveur (banc hors réseau, CPU Xeon 2,8 GHz, 60 Hz)

| Joueurs (bots) | Tick moyen | p95 | p99 | Max | Patch reçu par client | Évènements par client | Kills / min |
|---|---|---|---|---|---|---|---|
| 15 | 1,8 ms | 2,7 ms | 3,4 ms | 13 ms | 23 Ko/s (moy. 392 o/patch) | 0,8 Ko/s | 6 |
| 25 | 4,1 ms | 6,1 ms | 7,4 ms | 16,7 ms | 40 Ko/s (moy. 689 o/patch) | 1,8 Ko/s | 17 |
| 60 | 10,6 ms | 13,6 ms | 17,5 ms | 35,7 ms | 93 Ko/s (moy. 1 588 o/patch, max 28 Ko) | 2,8 Ko/s | 35 |

- Budget d'un tick à 60 Hz : **16,7 ms**. La croissance du coût est plus que linéaire avec le nombre de joueurs.
- À 60 joueurs, un patch dépasse le buffer par défaut de `@colyseus/schema` (avertissement « buffer overflow »).
- Bande passante sortante d'une room pleine : 93 Ko/s × 60 clients ≈ **5,6 Mo/s (~45 Mbit/s)**. Pour un joueur mobile : ~330 Mo/heure à 60 joueurs, ~83 Mo/heure à 15.
- Test 100 % bots : les bots coûtent plus cher que des humains (IA), donc ces chiffres sont pessimistes pour le CPU, pas pour le réseau.
- Lames au sol : stables (~270 à 15 joueurs, ~400 à 60) sur 10 minutes. Pas d'emballement malgré l'absence de TTL (cf. [GAME-11](#game-11)).

### Profil CPU (60 bots)

| Part du temps total | Fonction |
|---|---|
| 57 % | `updateBladePositions` (`server/src/systems/orbitPositions.ts`), dont 43 % dans la boucle d'aimantation des lames au sol |
| 14 % | `resolveCollisions` |
| 10 % | `updateMovement`, dont 7 % dans `pushOutPlayers` |
| 7 % | `BotController.update` |
| ~39 % (self) | Accesseurs `@colyseus/schema` (lecture de champs synchronisés dans les boucles chaudes) |
| ~14 % (self) | Accesseurs de ré-export CommonJS de `@bladeio/shared` (constantes lues dans les boucles chaudes) |
| ~13 % (self) | `MapSchema.forEach` (parcours répétés de `players` et `blades` dans chaque système) |

Les lignes « self » mesurent le temps passé dans la fonction elle-même, réparti sur tous les systèmes ; elles se recoupent avec les lignes inclusives du dessus.

### Client

| Mesure | Valeur |
|---|---|
| Trafic WebSocket réel reçu (1 humain + 10 bots) | 15-17 Ko/s, ~70 trames/s |
| Bundle JS de production | 1,24 Mo (328 Ko gzip), un seul chunk, sourcemaps publiées |
| Musiques | 8 pistes, 38 Mo au total (4-6 Mo par piste), chargées en streaming |
| Sessions automatisées desktop | 6, dont 4 terminées par une mort en ~10 s (3 par des bots, 1 par la bordure) |

### Dépendances

`npm audit --omit=dev` : **15 vulnérabilités** (1 haute : `nanoid` via `@colyseus/core` ; 11 modérées ; 3 basses). La majorité vient du méta-paquet `colyseus`, qui n'est pas utilisé par le code.

## 4. Points forts à préserver

- **Architecture autoritative propre** : le client n'envoie que `{dx, dy, boost, throw}` ; la simulation complète est côté serveur, découpée en systèmes lisibles (`movement`, `collisions`, `throws`, `pickup`…), avec un broad phase par propriétaire efficace pour les duels.
- **Contrat `shared/`** centralisé : constantes de gameplay, types de messages, géométrie des orbites et colliders de décor partagés client/serveur.
- **Qualité des commentaires** : ils expliquent le pourquoi (contraintes, bugs résolus). `CLAUDE.md` est un vrai guide de contribution.
- **Système de thèmes** bien pensé : trois niveaux de shader de sol, variables CSS injectées au boot, décor par variante, musique par thème, skill dédiée.
- **Presets de qualité** avec détection GPU, résolution dynamique, `InstancedMesh` pour les lames et le décor.
- **Juice déjà présent** : hitlag, knockback, screen shake réservé aux combats du joueur local, SFX atténués selon la distance, évènements de tier-up.
- **Bots crédibles** : personnalités, scoring multi-facteurs, prédiction d'interception, hystérésis de cible, anti double aggro.
- **Parcours social de base** : rooms privées à code, lien d'invitation copiable, JOIN qui échoue proprement sur un code inconnu, reconnexion de 20 s, chat protégé contre le XSS et limité côté serveur.
- **Flux invité → compte** soigné : wallet invité signé HMAC, transfert atomique au sign-in, RLS Supabase correctes (hors prix, cf. [ECO-01](#eco-01)).

## 5. Constats détaillés

Format : **ID — titre** (priorité). Constat, preuve (`fichier:ligne`), impact, recommandation, tâches du plan.

### A. Gameplay et game design

<a id="game-01"></a>
**GAME-01 — La progression plafonne à 20 lames** (P1)
- Constat : `TIER_THRESHOLDS = [1, 10, 20]` (`shared/src/constants.ts:80`). Au-delà de 20 lames, plus aucun palier visuel ni mécanique, alors que `MAX_BLADES_PER_PLAYER = 500` (`shared/src/constants.ts:34`). Le bandeau du lobby annonce « TIER 0 ARROW / TIER 1 SWORD / TIER 2 SCYTHE » (`client/index.html:264`) mais une seule géométrie d'épée existe, simplement agrandie (`client/src/entities/BladeView.ts:17-106`, `TIER_VISUAL_SCALE`).
- Impact : après une ou deux minutes de jeu, grossir ne procure plus de sensation de puissance nouvelle. C'est le moteur principal d'un `.io` qui s'éteint.
- Recommandation : 5 à 6 paliers avec des formes distinctes (flèche, épée, faux, scie, etc.), des jalons à 25/50/100/200 lames avec un retour visuel et sonore marqué, et une courbe de hitbox qui ne dérape pas (cf. GAME-02).
- Plan : 4.1.

<a id="game-02"></a>
**GAME-02 — Snowball sans contre-mesure** (P1)
- Constat : le nombre de lames sert à la fois de points de vie et de puissance offensive, et la hitbox des lames grossit avec le tier (×1,5 → ×3,0, `shared/src/constants.ts:88`). Au contact, le plus gros gagne presque toujours. Le leader porte une couronne visible par tous (`client/src/main.ts:961-988`), sans prime associée.
- Impact : les parties se figent autour d'un ou deux joueurs dominants ; les petits joueurs n'ont d'autre option que fuir.
- Recommandation : prime sur le leader (bonus de trophées et de loot), rendements décroissants au-delà d'un seuil, bonus « underdog » pour un kill contre plus gros que soi.
- Plan : 4.2.

<a id="game-03"></a>
**GAME-03 — Première minute punitive** (P1)
- Constat : le point de spawn est tiré jusqu'à ~194 u du centre alors que la zone mortelle commence à 248 u ; la seule contrainte est d'être à 25 u des joueurs vivants (`server/src/rooms/ArenaRoom.ts:83-108`). Les bots agressifs et chasseurs poursuivent toute cible pas plus forte qu'eux dans un rayon de 80 u, sans exception pour un joueur qui vient d'apparaître (`server/src/systems/bots.ts:365-441`) ; seule la protection de 2,5 s les retient. Un nouveau joueur a 3 lames, soit la cible idéale.
- Mesure : sur 6 sessions automatisées (joueur scripté qui reste immobile puis marche au hasard), 4 se terminent par une mort dans les ~10 premières secondes : 3 tuées par un bot, 1 par la bordure (capture [03](audit-2026-09/03-mort-bordure.jpg)).
- Impact : c'est le moment où un `.io` perd le plus de joueurs. Une mort sans comprendre pourquoi, dès la première partie, fait fermer l'onglet.
- Recommandation : spawn sûr (loin des bots et de la bordure, près de lames au sol), période de grâce pendant laquelle les bots ignorent les joueurs fraîchement apparus, feedback clair de la protection, tutoriel.
- Plan : 3.2, 3.1, 3.3.

<a id="game-04"></a>
**GAME-04 — La visée est la direction de déplacement** (P1)
- Constat : le lancer utilise `p.dirX/p.dirY`, c'est-à-dire la dernière direction de mouvement (`server/src/systems/throws.ts:64-69`). Au clavier, seules 8 directions sont possibles. À la souris, il faut marcher vers la cible pour la viser.
- Impact : plafond de compétence bas, et le lancer pousse à foncer dans le danger au lieu de tenir la distance. C'est pourtant la mécanique la plus « skill » du jeu.
- Recommandation : champ d'input `aim` séparé du mouvement (souris = visée, clavier = déplacement ; sur mobile, glisser depuis le bouton THROW ou réutiliser la direction du joystick).
- Plan : 1.3.

<a id="game-05"></a>
**GAME-05 — Un seul mode, sans fin** (P1)
- Constat : seul le FFA infini existe. Le README promet « short matches, instant replay ».
- Impact : pas de climax, pas de podium, pas d'objectif de session ; les joueurs ne savent pas quand « une partie » est finie.
- Recommandation : manches chronométrées (par exemple 5 minutes, zone qui se resserre à la fin, podium), puis modes équipe (Module 9 de l'ancien plan).
- Plan : 7.1, 7.2.

<a id="game-06"></a>
**GAME-06 — Carte statique, grande et vide pour les petites rooms** (P2)
- Constat : `MAP_RADIUS = 250` (≈ 196 000 u²) quel que soit le nombre de joueurs. En room privée à 2 ou 3 amis (bots désactivés par défaut, `server/src/rooms/ArenaRoom.ts:130`), on se cherche longtemps. Aucun évènement dynamique.
- Recommandation : rayon jouable qui s'adapte à la population, évènements de carte (pluie de lames, caisse légendaire annoncée, zone bonus), structures qui créent des points d'intérêt.
- Plan : 4.4, 4.5, 4.7.

<a id="game-07"></a>
**GAME-07 — Risque de « clash-lock »** (P2, à valider en playtest)
- Constat : chaque contact lame contre lame applique un hitlag de 50 à 110 ms aux deux joueurs, qui fige à la fois le mouvement et la rotation des orbites (`server/src/systems/collisions.ts:289-296`, `server/src/systems/movement.ts:92-103`, `server/src/systems/orbitPositions.ts:72-76`). Le knockback continue de décroître pendant le gel, donc il est en partie perdu.
- Impact probable : avec beaucoup de lames en contact, les hitlags s'enchaînent et les deux joueurs restent figés, sans possibilité de fuir.
- Recommandation : limiter la fréquence du hitlag par joueur (cooldown), ne pas geler l'orbite, appliquer le knockback à la sortie du gel.
- Plan : 1.6.

<a id="game-08"></a>
**GAME-08 — Power-ups trop longs et identifiables par la seule couleur** (P2)
- Constat : durée légendaire de 90 s (`shared/src/constants.ts:286-291`) ; un Spin ×1,6 ou un Shield pendant 90 s déséquilibre les combats. Les cinq types ne se distinguent que par la couleur (`client/src/entities/PowerUpView.ts`), qui change en plus selon le thème.
- Recommandation : durées de l'ordre de 8 à 25 s, une forme ou une icône par type, un son distinct par type.
- Plan : 4.3, 3.8.

<a id="game-09"></a>
**GAME-09 — Les bushes ne cachent rien aux bots et ne cachent que côté client** (P2)
- Constat : le masquage est purement visuel (`shared/src/decor.ts:77-88`, `client/src/main.ts:915-925`). Les bots n'appellent jamais `isInBush` et voient tout le monde.
- Impact : se cacher ne sert à rien contre les bots, qui représentent souvent la majorité des adversaires. Côté sécurité, cf. [SEC-03](#sec-03).
- Plan : 4.6, 2.4.

<a id="game-10"></a>
**GAME-10 — Le loot de mort privilégie les lames les plus anciennes** (P3)
- Constat : les lames dropées sont les N premières de `bladeIds`, donc les plus anciennes (souvent les Communes de départ) ; les plus récentes, souvent plus rares, sont détruites (`server/src/rooms/ArenaRoom.ts:569-578`).
- Recommandation : tirage aléatoire ou priorité aux lames rares, pour que tuer un joueur riche soit visiblement payant.
- Plan : 4.2.

<a id="game-11"></a>
**GAME-11 — TTL des lames au sol déclaré mais jamais appliqué** (P3)
- Constat : `GROUND_BLADE_TTL_MS = 15000` (`shared/src/constants.ts:178`) et `expiresAt` sont posés sur les lames au sol, mais `expiresAt` n'est lu que pour les projectiles (`server/src/systems/throws.ts:137`). Les commentaires se contredisent (`shared/src/constants.ts:176-177` et `server/src/systems/orbitPositions.ts:44-46`).
- Impact mesuré : faible (pas d'accumulation sur 10 minutes), mais le comportement réel n'est pas celui documenté.
- Recommandation : trancher (appliquer le TTL avec un fondu visuel, ou supprimer la constante).
- Plan : 0.9.

### B. Game feel et lisibilité du combat

<a id="feel-01"></a>
**FEEL-01 — Les lames affichées ne sont pas là où le serveur les calcule** (P0)
- Constat : le serveur calcule l'angle orbital avec son horloge `elapsed`, qui démarre à la création de la room (`server/src/rooms/ArenaRoom.ts:369`, `server/src/systems/orbitPositions.ts:94`). Le client utilise son propre `elapsed`, qui démarre au chargement de la page et s'arrête quand l'onglet est en arrière-plan (`client/src/main.ts:890` et `927`, `client/src/entities/BladeView.ts:385`). Rien ne synchronise les deux (`state.tick` n'est jamais lu côté client). Le client n'applique pas non plus le multiplicateur du power-up Spin (`server/src/systems/orbitPositions.ts:90-93` contre `client/src/entities/BladeView.ts:386`).
- Impact : chaque client voit les orbites avec un déphasage arbitraire. Des lames se croisent à l'écran sans clash, des clashs et des kills arrivent sans contact visible, et les étincelles de clash apparaissent là où aucune lame n'est dessinée. L'écart est le plus visible dans les duels à peu de lames (3 contre 3), où chaque lame compte. C'est le défaut n°1 du ressenti de combat.
- Recommandation : horloge serveur dérivée du numéro de tick, estimation de l'offset côté client, angles calculés au même instant que la position interpolée, prise en compte du Spin.
- Plan : 1.1.

<a id="feel-02"></a>
**FEEL-02 — La prédiction locale est un lissage, sans rejeu d'inputs** (P1)
- Constat : à chaque patch, le client recale sa position prédite sur la position serveur puis absorbe l'écart en ~150 ms (`client/src/main.ts:720-746`). Le numéro de séquence est envoyé et synchronisé (`lastSeq`) mais jamais utilisé pour rejouer les inputs non acquittés. `simulateStep` ignore le power-up Speed, le knockback et le hitlag (`client/src/main.ts:680-696`).
- Impact : effet élastique aux changements de direction et aux arrêts, compensation trop forte ou trop faible selon le ping, corrections visibles sous Speed et lors des clashs.
- Recommandation : tampon d'inputs horodatés, rejeu depuis `lastSeq` à chaque patch, simulation locale de Speed, du knockback et du hitlag.
- Plan : 1.2.

<a id="feel-03"></a>
**FEEL-03 — Direction souris calculée en espace écran** (P1)
- Constat : la direction est le vecteur centre de l'écran → curseur (`client/src/input/Mouse.ts:39-48`), alors que la caméra est inclinée d'environ 50°. L'angle à l'écran ne correspond pas à l'angle au sol (compression verticale), et ce vecteur sert aussi à viser.
- Recommandation : projeter le curseur sur le plan du sol (raycast) et viser depuis la position du joueur.
- Plan : 1.4.

<a id="feel-04"></a>
**FEEL-04 — Caméra figée, dépendante du thème et du format d'écran** (P2)
- Constat : décalage constant, pas de zoom selon la taille de l'orbite (rayon jusqu'à ~9 u), champ vertical fixe de 55° (`client/src/scene/Scene.ts:47-52`). En portrait mobile, le champ horizontal devient très étroit (capture [08](audit-2026-09/08-mobile-combat.jpg)). Le décalage caméra est défini par le thème (neon `y=22, z=16` dans `client/src/themes/neon.ts:172`, sanctuaire `y=19, z=17` dans `client/src/themes/sanctuaire.ts:294`, etc.) : un thème payant change la zone visible, ce qui contredit le principe « pas de pay-to-win » de `CLAUDE.md`.
- Recommandation : cadrage défini comme une constante de gameplay dans `shared/`, zoom arrière progressif avec la taille, adaptation au ratio d'écran pour garantir la même surface visible pour tous.
- Plan : 1.7.

<a id="feel-05"></a>
**FEEL-05 — Retours de combat incomplets** (P2)
- Constat : pas de fil des éliminations, pas de « +N » au kill, pas de flash sur la lame touchée, pas d'indication de la direction d'un coup, pas de barre de vie des caisses (la valeur `hp` est stockée mais jamais affichée, `client/src/entities/CrateView.ts:72-77`), le même son pour un kill et une caisse détruite (`client/src/main.ts:385-388`).
- Plan : 3.4, 1.5.

<a id="feel-06"></a>
**FEEL-06 — Un joueur déconnecté continue d'avancer** (P1)
- Constat : pendant les 20 s de `allowReconnection` (`server/src/rooms/ArenaRoom.ts:271-277`), le joueur conserve son dernier input ; `lastInputAt` est écrit mais jamais lu (`server/src/rooms/ArenaRoom.ts:338`).
- Impact : une coupure réseau d'une seconde peut suffire à envoyer le joueur dans la bordure ou dans un ennemi.
- Recommandation : remettre les inputs à zéro à la déconnexion et après ~500 ms sans input.
- Plan : 0.5.

<a id="feel-07"></a>
**FEEL-07 — Les timers comparent l'horloge du serveur à celle du client** (P2)
- Constat : `speedUntil`, `spinUntil`, `magnetUntil`, `shieldUntil`, `spawnProtectionUntil` et `throwCooldownUntil` sont des dates absolues de l'horloge du serveur, comparées à `Date.now()` du navigateur (`client/src/main.ts:761-784` pour les badges d'effets, `client/src/main.ts:904-912` pour le halo de protection).
- Impact : si l'horloge du joueur est décalée (fréquent de quelques secondes, parfois de plusieurs minutes), les durées affichées et le halo de protection sont faux.
- Recommandation : exprimer ces échéances dans le temps serveur synchronisé de la tâche 1.1.
- Plan : 1.8.

### C. Netcode et performance serveur

<a id="net-01"></a>
**NET-01 — Bande passante élevée** (P1)
- Constat : tick et patch à 60 Hz (`server/src/rooms/ArenaRoom.ts:147-148`). Chaque lame en orbite est une entité synchronisée ; chaque ramassage, perte ou lancer recompacte les `slotIndex` de tout un anneau (`server/src/systems/orbitPositions.ts:180-189`). Mesures : 23 Ko/s par client à 15 joueurs, 93 Ko/s à 60 joueurs (cf. section 3).
- Impact : une room pleine sature l'upload d'une connexion domestique (le `Caddyfile` indique un auto-hébergement) ; coût data élevé sur mobile.
- Recommandation : patch à 20-30 Hz avec interpolation (le tick peut rester à 60 Hz), quantification des positions, filtrage par zone d'intérêt (`StateView` de Colyseus 0.16), et à terme synchroniser la composition des orbites par joueur plutôt que chaque lame.
- Plan : 2.3, 2.4, 2.5.

<a id="net-02"></a>
**NET-02 — Coût du tick proche du budget à 60 joueurs** (P1)
- Constat : 10,6 ms en moyenne et 17,5 ms au p99 pour un budget de 16,7 ms. Profil : la boucle d'aimantation parcourt chaque lame au sol × chaque joueur via les accesseurs du schema, appelle `Date.now()` environ 24 000 fois par tick et lit des constantes à travers les ré-exports CommonJS (`server/src/systems/orbitPositions.ts:127-158`) ; `pushOutPlayers` recalcule le rayon de bouclier pour chaque paire (`server/src/systems/movement.ts:34-66`) ; les `MapSchema.forEach` sont répétés dans chaque système.
- Impact : Node est mono-thread ; deux rooms pleines dans le même process dépassent le budget et le jeu ralentit pour tout le monde.
- Recommandation : tableaux simples reconstruits une fois par tick, constantes et `now` sortis des boucles, grille spatiale pour l'aimantation, rayon de bouclier précalculé. Objectif : moins de 4 ms à 60 joueurs.
- Plan : 2.1, 2.2, 2.8.

<a id="net-03"></a>
**NET-03 — Validation des inputs incomplète** (P3)
- Constat : `violations` et `MAX_INPUT_VIOLATIONS` ne sont jamais utilisés (`server/src/state/Player.ts:79`, `shared/src/constants.ts:19`) ; au-delà de 80 inputs/s, les messages sont simplement ignorés. Le README annonce un kick après 3 violations et une limite de 40 inputs/s.
- Plan : 0.8.

<a id="net-04"></a>
**NET-04 — Petits pièges de code serveur** (P3)
- `lastHitAt` est une `Map` de module partagée par toutes les rooms du process (`server/src/systems/collisions.ts:40`).
- `attachBladeToPlayer` écrase `player.score` avec `maxBladeCount` avant le recalcul de fin de tick (`server/src/systems/pickup.ts:48`) ; sans effet visible aujourd'hui, mais trompeur.
- `attachBladeToPlayer` et `recompactOwnerRing` parcourent toutes les lames de la room à chaque appel (`server/src/systems/pickup.ts:21-26`, `server/src/systems/orbitPositions.ts:180-189`).
- Plan : 2.2.

## 6. Ce qui manque pour en faire un bon jeu

Comparaison avec ce qui fait tenir les `.io` qui durent (agar.io, slither.io, diep.io, et les jeux de lames en orbite popularisés sur mobile).

| Pilier du genre | État | Ce qui manque |
|---|---|---|
| Jouer en un clic | Oui | Quick Play et mode invité fonctionnent. |
| Combat lisible et juste | Non | Synchronisation visuelle des orbites, vraie prédiction, visée indépendante. |
| Première minute réussie | Non | Spawn sûr, tutoriel, bordure lisible, bots moins prédateurs envers les nouveaux. |
| Montée en puissance visible | Partiel | Paliers au-delà de 20 lames, formes distinctes, jalons. |
| Décisions risque / récompense | Oui | Boost payant, lancer qui consomme une lame, bordure mortelle. |
| Contre-mesures au snowball | Non | Prime sur le leader, rendements décroissants. |
| Retours immédiats | Partiel | Couronne et classement existent ; manquent fil des éliminations, « +N », sons distincts. |
| Objectifs de session et raisons de revenir | Non | Record personnel, défis, XP, classements du jour et de la semaine. |
| Identité et social | Non | Tous les joueurs se ressemblent ; pas de skins visibles ; partage sans aperçu. |
| Variété | Non | Un seul mode, carte statique, aucun évènement. |
| Tourne partout | Partiel | Presets de qualité solides ; mobile perfectible ; bande passante lourde. |
| Serveurs stables | Partiel | Un seul serveur ; chaque déploiement coupe les parties. |
| Économie saine | Non | Prix serveur, pas de farm, cosmétiques qui se voient. |

En résumé : les correctifs urgents (économie exploitable, données factices, runs perdues sur une déconnexion ou un reload) sont courts et passent en premier (phase 0 du plan). Ensuite, par ordre d'importance pour le plaisir de jeu :

1. **Rendre le combat fiable** (ce qu'on voit est ce qui se passe, la réponse aux inputs est immédiate, on vise ce qu'on veut).
2. **Réussir la première minute** (on comprend, on survit, on progresse vite).
3. **Donner une courbe de puissance qui ne plafonne pas** et des contre-mesures au snowball.
4. **Donner des raisons de revenir** (profil, XP, défis, classements temporaires).
5. **Créer de la variété** (manches courtes, évènements, modes).
6. **Rendre les joueurs reconnaissables** et vendre des cosmétiques qui se voient.
7. **Tenir la charge et déployer sans casser les parties.**

### B. Reproduire les mesures serveur

```bash
npm install
npm run build:shared
npm run build --workspace=@bladeio/server
node tools/bench-server.js 60 300    # 60 bots, 5 minutes simulées
node tools/bench-server.js 15 120    # 15 bots, 2 minutes simulées
```

Le script affiche le coût du tick (moyenne, p50, p95, p99, max), la taille des patchs reçus par un client, le volume d'évènements et un échantillon toutes les 30 s simulées (joueurs en vie, lames au sol, en orbite, en vol). Profil CPU : ajouter `node --cpu-prof` devant la commande.
